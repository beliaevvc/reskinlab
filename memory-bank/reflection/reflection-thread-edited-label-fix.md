# Рефлексия: Ложная «(ред.)» при старте треда

## Метаданные
- Дата: 2026-04-01
- Уровень сложности: 2
- Задача: При первом ответе в треде у корневого сообщения появлялась пометка «(ред.)», хотя текст не редактировали.

## Резюме
Заменили generic-триггер `update_updated_at_column()` на comments-специфичный `update_comments_updated_at_smart()`, который обновляет `updated_at` только при изменении пользовательского контента (`content`, `attachments`, `scheduled_at`), а при изменении метаданных (thread-статистика, пины) сохраняет прежнее значение. Фронт — RPC `mark_comment_thread_root` вместо прямого `UPDATE` в хуке.

## Что прошло хорошо
- Диагностика root cause была быстрой: `updated_at !== created_at` в `CommentItem.jsx`, триггер, триггерные функции — цепочка очевидная.
- Паттерн RPC с `SECURITY DEFINER` уже был в проекте (`publish_scheduled_comment`, `pin_comment`), поэтому был готовый образец.

## Сложности
- **Первый подход (DISABLE TRIGGER) провалился дважды:**
  1. Триггерные функции `update_thread_stats` / `decrement_thread_stats` забыли пометить `SECURITY DEFINER` — `ALTER TABLE` от имени authenticated давал 403 (`42501: must be owner of table`).
  2. После добавления `SECURITY DEFINER` — PostgreSQL запретил `ALTER TABLE` на таблице, которая используется в текущей сессии (`55006: cannot ALTER TABLE because it is being used by active queries`). `ALTER TABLE ... DISABLE TRIGGER` внутри AFTER INSERT триггера на ту же таблицу — невозможно.
- **Второй подход (smart trigger) сработал** — вместо отключения триггера, заменили логику самого триггера: проверяем, изменился ли контент, и если нет — не трогаем `updated_at`.

## Уроки
- **`ALTER TABLE ... DISABLE/ENABLE TRIGGER` — не универсальный приём.** Работает только в отдельных RPC-вызовах, но не внутри триггеров на ту же таблицу. Для триггеров нужен smart-подход с проверкой `IS NOT DISTINCT FROM`.
- **Fallback-паттерн полезен:** фронт пробует RPC, при ошибке фоллбэчит на обычный UPDATE — позволяет деплоить фронт до/после миграции.
- **Runtime-логирование критически важно:** без логов ошибки `42501` и `55006` были бы неотличимы от «не работает».
- **Паттерн smart trigger можно переиспользовать:** любые метаданные (пины `is_pinned`, `pin_name` и т.д.) теперь тоже не бампят `updated_at` — побочный позитивный эффект.

## Улучшения процесса
- При работе с PostgreSQL-триггерами: сначала проверять, можно ли менять DDL из контекста триггера (в данном случае — нельзя).
- Миграции, содержащие `ALTER TABLE`, тестировать через INSERT/UPDATE, а не только через прямой вызов RPC.
